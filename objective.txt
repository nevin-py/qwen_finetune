You are the lead ML engineer responsible for designing and implementing this entire project.

## PROJECT

Build a serious, portfolio-grade **Text-to-SQL Fine-Tuning, Execution-Based Verification, and Repair System**.

The goal is NOT to build another SQL chatbot.

The goal is to experimentally answer:

> Can a small open-source language model be fine-tuned for text-to-SQL, and can execution-based verification and automatic repair improve its end-to-end correctness?

The final project should demonstrate:

* ML/data engineering
* LLM fine-tuning
* QLoRA/LoRA
* reproducible experiments
* benchmark evaluation
* SQL parsing and validation
* database execution
* execution-based correctness
* automatic error analysis
* iterative SQL repair
* inference/deployment
* resource-aware ML engineering

The project must be feasible on approximately:

* NVIDIA RTX 3050 Laptop
* 4 GB VRAM
* 16 GB system RAM

Do NOT design a system requiring large GPUs.

Use these three datasets as the primary datasets:

Use Spider as the primary supervised text-to-SQL dataset.

* standard text-to-SQL evaluation
* schema generalization

## SParC

Use SParC for conversational/multi-turn text-to-SQL experiments.

Do not allow SParC to unnecessarily complicate the first working version.

Then add SParC as an extension if the architecture supports it cleanly.

## BIRD

Use BIRD as the primary difficult held-out benchmark.

The model must NOT train on the BIRD evaluation data.

Use the official benchmark/evaluation methodology where possible.

BIRD should represent the project's external/generalization test.

Do not contaminate BIRD evaluation through training, synthetic augmentation, prompt examples, or hyperparameter tuning against the test set.

If a public development split is available, use that for development and reserve the official test evaluation appropriately.

# 5. BASELINE FIRST

Before fine-tuning anything, build a working baseline.

Choose a small open-source instruction/code model that can realistically run under the hardware constraints.

Candidates may include appropriate small Qwen/Gemma/other open-source models, but verify current availability, license, VRAM requirements, and Hugging Face compatibility before choosing.

Prefer approximately 1B–3B parameters if practical.

The model selection should be justified by:

* parameter count
* context length
* tokenizer
* SQL/code capability
* quantization support
* license
* expected VRAM
* training feasibility on 4 GB VRAM

The baseline must support:

INPUT:

Natural language question + database schema

OUTPUT:

SQL

Measure:

* generation latency
* memory/VRAM usage where possible
* syntactic validity
* execution validity
* execution accuracy

Do not fine-tune before this baseline works.

# 8. EXPERIMENT MATRIX

Do not randomly experiment.

Create a small controlled experiment matrix.

At minimum:

### Experiment A

Base model with prompting.

### Experiment B

Base model + LoRA/QLoRA fine-tuning.

### Experiment C

Fine-tuned model + execution-based verification.

### Experiment D

Fine-tuned model + verification + automatic repair.

The purpose is to isolate the contribution of each component.

Do not claim verification improves generation itself.

Measure whether it improves the final end-to-end result.

# 9. SQL VERIFIER

This is the central engineering component.

Build a verifier that receives:

* generated SQL
* database/schema
* optionally the original question
* gold SQL/results when available for evaluation

It should perform multiple checks.

## Layer 1 — SQL parsing

Determine whether the SQL is syntactically valid.

Use a proper SQL parser rather than regex wherever possible.

---

## Layer 2 — Schema validation

Check:

* table existence
* column existence
* obvious invalid references
* aliases
* basic type/structure issues where practical

---

## Layer 3 — Safety validation

The system should operate in a read-only environment.

Reject or prevent:

* DROP
* DELETE
* UPDATE
* INSERT
* ALTER
* TRUNCATE
* CREATE
* destructive operations

Do not rely solely on the model behaving correctly.

Use database-level permissions/sandboxing as an additional safety boundary.

---

## Layer 4 — Execution

Execute candidate SQL against the benchmark database.

Use:

* read-only database users where possible
* query timeouts
* resource limits
* transaction rollback/isolation
* controlled database copies for evaluation

Never execute arbitrary generated SQL against a valuable production database.

---

## Layer 5 — Result comparison

For benchmark evaluation, compare the candidate's execution result with the expected result according to the benchmark's established methodology.

Handle carefully:

* row ordering
* NULLs
* numeric precision
* duplicate rows
* column ordering
* database-specific semantics

Do NOT simply compare raw strings.

---

# 10. IMPORTANT: GOLD SQL ≠ ONLY CORRECT SQL

The verifier must understand that two different SQL queries can produce the same correct result.

Therefore:

DO NOT define correctness solely as:

candidate SQL == gold SQL

Use execution-based correctness wherever the benchmark methodology permits it.

You may still report exact/structural SQL matching as a secondary diagnostic metric.

---

# 11. AUTOMATIC REPAIR

Implement a repair loop.

Example:

Question
↓
Model
↓
Candidate SQL
↓
Verifier
↓
Failure
↓
Error information
↓
Model repair
↓
Candidate SQL v2
↓
Verifier
↓
Success / failure

Limit repair attempts, e.g. 1–3.

Do not create an infinite agent loop.

The repair prompt should contain only useful information, such as:

* SQL error
* relevant schema information
* original question
* previous SQL

Avoid blindly dumping huge database contents into the model.

---

# 12. REPAIR EXPERIMENT

Measure:

### Generation only

How often does the model generate correct SQL?

### Generation + verification

How often can the system detect incorrect SQL?

### Generation + verification + repair

How often can the system recover from incorrect SQL?

Report all three separately.

The verifier must not magically receive the gold SQL during real inference.

Gold SQL/result information may only be used by the evaluation harness to determine whether the system was correct.

This distinction is critical.
